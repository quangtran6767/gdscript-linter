## Task 1: `declaration-order` rule

Behavior:

- Id `declaration-order`, level **warning**, enabled by default, group
  "Naming and style" in `docs/rules.md`.
- Order is exactly the formatter's: reuse `crate::reorder::build_reorder_plan`
  (`src/reorder.rs`). Don't write a second ordering. The plan sorts within
  each `#region` group, keeps comments and annotations attached, and splits
  inline `class_name X extends Y`.
- Report when the plan's item order differs from source order. One
  diagnostic per file, spanning the first declaration that is out of place.
  The message names that declaration and what it should come before, e.g.
  ``signal `died` should come before variables``. Keep the text stable.
- Top level only, like the formatter. Inner classes aren't checked.
- Files with `# fmt: off` regions: report, but attach no fix (the formatter
  skips reordering there for the same reason, see `process_source` in
  `src/formatter.rs`).
- Files with parse errors: no report (consistent with other syntax rules).

Fix:

- The fix moves declarations. It must not reformat code inside them.
  Acceptable implementations: build the new text from the source slices of
  plan items (each with its attached comments/annotations), or, only when
  `fix::is_formatted(source, ...)` is true, use `format_gdscript` with
  `reorder_code = true`. Either way, for a formatted input the result must
  equal what `gdguard --reorder-code` produces. Test this against the inputs
  in `tests/reorder_code/input`.
- Safety: **safe**, except **unsafe** when a variable's initializer references
  a member variable declared before it in the source but after it in the new
  order (member initializers run in declaration order, so this can change
  behavior). Both `var a = 1` / `@export var b = a` and
  `var a = 1` / `@export var b = a + 1` become unsafe when `b` moves above `a`.
  Check every dependency pair, even if a variable keeps the same item index.
  Constants, enums, signals, methods and inner classes moving is safe.
- After the fix, re-linting must report no `declaration-order` diagnostic
  (fix/re-lint loop is the product priority).

Plumbing (same as the W9 rules):

- `src/linter/rules/declaration_order.rs`, registered in
  `src/linter/rules.rs` (the `RuleDefinition` table). It is syntax-only,
  so it does not belong in `SEMANTIC_RULE_IDS`.
- Metadata, rationale and bad/good examples in `src/linter/rules_meta.rs`
  (shown by `gdguard explain declaration-order`).
- `docs/rules.md`: table row and section; update the rule count (39 to 40).
  `tests/explain/main.rs` fails if this is wrong.
- `docs/specification_linter.md` (rule list and fix engine notes),
  `CHANGELOG.md`, `docs/implementation_plan.md` (add a W10 entry).
- Tests: `tests/lint/input/declaration_order.gd` + `tests/lint/expected/`,
  fix tests in `tests/fix/` (safe vs unsafe case, region groups, comments
  and annotations moving with their declaration, `# fmt: off` gives no fix,
  re-lint is clean), and one CLI test for `lint --fix` on a file out of order.
- Existing snapshots will gain diagnostics where fixtures are out of order
  (`tests/lint/spans/all_rules.txt`, `tests/e2e/expected`, maybe others).
  Update them only after checking each new diagnostic is right. Don't
  reorder existing fixtures to hide diagnostics unless the fixture is about
  another rule and the new diagnostic is noise for it.

Contracts: no frozen signature, JSON schema or config schema changes. A new
rule id is additive. Users turn it off with
`[rules] declaration-order = "off"`.

## Rules

**[All built-in rules, with examples →](docs/rules.md)** ·
